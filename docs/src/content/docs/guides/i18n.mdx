Astro Xitter ships with built-in [internationalization](https://developer.mozilla.org/en-US/docs/Glossary/Internationalization) (i18n) which is applied to the following elements:

- Numeric elements, such as like and reply count
- Date and time, such as tweet creation date

The locale used for i18n is derived from [`Astro.currentLocale`](https://docs.astro.build/en/reference/api-reference/#currentlocale) for static rendering. For [on-demand rendering mode](/guides/on-demand) however, [`Astro.preferredLocale`](https://docs.astro.build/en/reference/api-reference/#preferredlocale) will be prioritized instead of `Astro.currentLocale`.

If both globals are `undefined`, Astro Xitter will resolve locale to `en-US` instead.

Aside from relying on Astro's globals, you can also supply the locale yourself by passing it to the `locale` prop.

<Tabs>
    <TabItem label="Astro">
        ```astro
        ---
        import { Xitter } from 'astro-xitter';
        ---

        <Xitter id="<TWEET_ID>" locale="id-ID" />
        ```
    </TabItem>

    <TabItem label="MDX">
        ```mdx
        ---
        title: title
        description: description
        ---

        import { Xitter } from 'astro-xitter';

        <Xitter id="<TWEET_ID>" locale="id-ID" />
        ```
    </TabItem>
</Tabs>

The above code will render the following tweet. Notice the difference between how the date is displayed and the unit used for like and reply count.

<Container>
    <Xitter id="20" locale="id-ID" />
</Container>

The supplied locale must be compatible with [`Intl.LocalesArgument`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl#locales_argument) interface.

## Digits and Clock

The digit set and the 12 or 24-hour clock are taken from the locale's [CLDR](https://cldr.unicode.org/) data, and that data does not always match X: recent CLDR releases resolve `ar` to Latin digits and `ja` to the 24-hour clock (`17:00`), while X renders Arabic-Indic digits and `午後5:00`.

Since `locale` accepts any [`Intl.LocalesArgument`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl#locales_argument), a specific behaviour can be requested with a [Unicode locale extension](https://www.unicode.org/reports/tr35/#Unicode_locale_identifier) rather than a dedicated prop:

```astro
<Xitter id="<TWEET_ID>" locale="ar-u-nu-arab" />
<Xitter id="<TWEET_ID>" locale="ja-u-hc-h12" />
```

- `-u-nu-` selects the [numbering system](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat/NumberFormat#numberingsystem), such as `arab`, `arabext`, `deva`, or `latn`.
- `-u-hc-` selects the [hour cycle](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat/DateTimeFormat#hourcycle): `h11`, `h12`, `h23`, or `h24`.

Because both counts and dates share the same formatter configuration, the chosen digits apply to both. Extensions can be combined in one tag, and the writing direction is still resolved from the base language, so `ar-u-nu-arab` keeps rendering right-to-left.

:::caution
The calendar is selected the same way, with `-u-ca-` — for example `ar-SA-u-ca-gregory`. Without it, `ar-SA` may render Hijri dates (`١٤ ربيع الآخر ١٤٤٨ هـ`) on runtimes that default to `islamic-umalqura`.
:::
